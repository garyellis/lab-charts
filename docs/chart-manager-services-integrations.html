chart-manager upgrade

cli/upgrade.py · 251 ln · 2 commands (1 hidden) · registered on the root appdependency intake

The intake stage of Flow 0. Ask Renovate to discover dependency updates for one wrapper chart and turn the completed update into one repeatable pull request. The module's own docstring states the split precisely: "the service owns discovery, preflight, isolated worktree mutation, and PR idempotency. This module owns only Typer's flag shape and stable rendering."

upgrade --path CHART_PATH --dry-run --format text|json → UpgradeService.upgrade(UpgradeRequest) → UpgradeResult upgrade-finalize --path CHART_PATH --data-file PATH (envvar RENOVATE_POST_UPGRADE_COMMAND_DATA_FILE) --format … → UpgradeFinalizer.finalize(FinalizeRequest) → FinalizeResult # hidden=True

Why two commands, and why one is hidden

  • upgrade is what an operator or a workflow runs. It resolves Path(".") as the repository root and never switches branches, stages files or commits in the caller's checkout — Renovate does its own platform checkout
  • upgrade-finalize runs inside Renovate's update branch, called back by postUpgradeTasks.commands. hidden=True keeps it out of --help: it is machine surface, not operator surface
  • The callback data file is taken from --data-file or the RENOVATE_POST_UPGRADE_COMMAND_DATA_FILE envvar, and a missing value is an explicit ChartManagerError rather than a silent no-op
  • Both commands go through _container() module-level factories — the same monkeypatch seam every other group uses

One renderer, two result types

  • _wire_payload projects either UpgradeResult or FinalizeResult onto one schema_version: 1 contract, preferring a result's own to_dict() and falling back to asdict
  • _render_text emits every contract field in a fixed order, including absent ones (-) — so a script grepping the text output does not break when a field is null
  • _json_value normalizes Path, Enum, mappings and tuples, and JSON is dumped sort_keys=True — deterministic bytes for automation
  • This is the one place the surface carries real logic. It is renderer-shaped (projection + formatting) rather than orchestration, but the _first(..., "current_wrapper_version", "current_version", …) alias-chasing is a smell: if the two result dataclasses converged on one field vocabulary, _wire_payload would shrink to a pass-through, and a second surface would not have to re-derive the same aliases
The hidden command is the security boundary, and it is treated like one. Renovate's post-upgrade execution is privileged by nature, so the trust is pinned in configuration rather than in the CLI: renovate-global.json sets allowShellExecutorForPostUpgradeCommands: false and constrains allowedCommands to a single anchored regex — ^chart-manager upgrade-finalize --path (?:[A-Za-z0-9][A-Za-z0-9._-]*/)+[A-Za-z0-9][A-Za-z0-9._-]*$. Nothing else in the repository can be executed from a Renovate branch, and the path shape is validated again by resolve_chart_path before any file is read. See the upgrader service panel for the containment rules.
Outcome vocabulary (UpgradeResult.outcome, rendered verbatim): dry_run · no_changes · pr_open (this run opened it) · pr_updated (a PR on the chart's deterministic branch already existed) · status_unknown. That last one is the interesting one — it is emitted when gh could not answer, so the command reports "Renovate ran, PR state unverified" instead of guessing no_changes. The failed lookup is also appended to diagnostics. Operator-facing detail lives in docs/renovate-upgrades.md.

The static gate has two entry shapes and one implementation. chart is optimized for local development; run preserves changed-file CI aggregation and repository health checks. Service-owned

  • chart and run are thin request adapters over one service and one private CLI execution boundary
  • values, namespace, release, Helm binding and validator policy come from the selected chart's strict chart-lifecycle.yaml rather than from flags
  • worklist assembly, targeted catalog loading, Helm grouping, validator provider construction, aggregation and retention all live below Typer
  • chart-path resolution raises typer.BadParameter at the edge via _bad_parameter, which translates a service-raised ValidateInputError rather than owning the rule

Surface-owned

  • _resolve_display — TTY/format-driven UI choice. Pure surface concern
  • _emit_result — format dispatch and the $GITHUB_STEP_SUMMARY opt-in. Surface concern
  • exit-code mapping via outcome.exit_code — the verdict comes from the result object; the shared _execute boundary owns the CLI's single process exit
  • --verbose ⇒ plain progress, plus the warning when it forces serial — UX behavior that belongs at the edge
One execution boundary, one owner per decision. chart() and run() both hand their request to _execute(), so display selection, service invocation, output emission, cleanup and exit semantics have a single home.

Promote a chart version into a Flux GitOps repo, then wait for and test the rollout. This group is already what the rest of the CLI should look like: request in, result out, renderer on top — and it got there without a separate use-case layer, just by being disciplined about the boundary. It is also where the promotion status model and the lifecycle-event emission live.

helmrelease promote --flux-repo --path --environment --chart-name --version --base-branch=main --dry-run --allow-downgrade → container.promote_service(confirm_downgrade=cb).promote(PromoteRequest) → PromoteResult(status: PromoteStatus, …) helmrelease monitor --chart --version --namespace --environment --concurrency=4 --per-poll-timeout=10s --per-hr-timeout=5m --total-timeout=15m --output=auto --no-color --fail-fast → container.monitor_service(progress=driver?).monitor(MonitorRequest) → MonitorResult = MonitorService(client=HelmReleaseClient(kubectl), kubectl=kubectl, events=writer) helmrelease test …monitor flags… --environment --pod-log-tail=200 (no --fail-fast) → container.test_service(progress=driver?).test(TestRequest) → TestResult = TestService(client=HelmReleaseClient(kubectl), kubectl=kubectl, helm=Helm(verbose=False), events=writer) # --environment is what arms lifecycle emission. Absent = ad-hoc run, emits nothing: # a placeholder environment would silently corrupt a real promotion timeline.

Why it works

  • One frozen request object per command. Every flag lands on MonitorRequest/TestRequest/PromoteRequest; the service validates its own fields. Nothing is "resolved" in the callback
  • Results carry the verdict. result.ok drives typer.Exit(1) — the CLI never decides pass/fail
  • Rendering is a separate module. The Rich renderers live in helmrelease_render.py; the services are rendering-agnostic and import no Rich
  • DI through overrideable factories, backed by the container. _make_monitor_service / _make_test_service / _make_promote_service are module-level so tests swap them, while their bodies delegate to _container(). The monkeypatch seam and the composition root coexist rather than one replacing the other
  • Interaction is a port, not a dependency. _confirm_downgrade is passed in as a callable, so PromoteService can ask a question without knowing what a terminal is. A Slack surface passes a callback that posts a button; a REST surface passes lambda *_: False and gets PromoteStatus.ABORTED back to map to 409

The only wrinkles

  • _resolve_output_mode raises ChartManagerError for a bad --output where typer.BadParameter would be the local idiom — trivial
  • The progress callback is wired only in pretty mode; JSON mode passes None. Correct, but it means progress events have no non-terminal consumer yet — a websocket surface would want them
  • The wire contract lives below the surface. services/helmrelease/wire.py owns SCHEMA_VERSION (public), monitor_to_dict and test_to_dict — pure result → dict, no file, no format=. The CLI's JSON path is three lines of json.dump around it
  • A JSON serializer looks exactly like presentation until you ask whether a second surface wants the identical bytes. That is test ② on the layering-rules panel, and the reason both versioned contracts — validate's JSON_SCHEMA_VERSION and helmrelease's SCHEMA_VERSION — are public and live in services/*/wire.py
  • The group is portable: a FastAPI route is ~10 lines around the same three calls, and it returns the same dict the CLI prints

Emit build- and promotion-lifecycle events from CI shell steps. The thinnest group in the tool, and the one place where a policy in the CLI is deliberate and correct.

  • Both commands are one call each; a Slack slash-command or webhook receiver is a direct EventWriter call with its own failure policy

Two tests, and you need both

① Does it change the answer, or only the appearance? --output auto changes only how a result is displayed — CLI. An authored namespace template changes what manifests are validated — service. ExposeService.apps_domain() determines the URL a user is told to open — service. This test sorts orchestration from surface.
② Would a second surface want this identically, or necessarily differently? This one sorts within the surface bucket. Identically ⇒ it is a contract, so it lives below cli/: an API, a Slack app, and a web UI all want the exact same JSON — if they don't get it from one function they diverge silently, both claiming schema_version: 1. Necessarily differently ⇒ it stays up: an HTTP server has no terminal, so there is nothing to share about isatty or a Rich Live table. Together the two tests produce the split on the surface panel.
The boundary that keeps ② from overshooting: push projections down, not rendering. to_json(result) -> dict in a service is right; emit(result, fmt="json", color=False, console=…) is wrong — the moment a service grows a format= parameter it starts growing color= and width=, and you have moved the UI down instead of the contract. Services expose pure result → dict/str functions; the surface picks one and does all the I/O.

The boundary holds in both directions

Presentation and orchestration meet at typed ports. Cluster services take an injected ProgressCallback and return DevelopmentClusterResult, EphemeralTestResult, or DevelopmentClusterActionResult. Why the rules are drawn here — and where they stop

✓ What the rules buy

  • Multi-surface is the forcing function. REST / GraphQL / RPC / Slack each re-answer "what does this command mean"; a command whose meaning lives only inside a Typer callback cannot be fronted twice
  • The capability boundary is concrete. Validation orchestration lives below Typer, and dependency planning stays an internal service capability rather than a separate product surface
  • Testability follows for free. Assembly in a command body is reachable only through CliRunner; the same logic behind a request/result boundary is a plain unit test with no terminal
  • The pattern is proven in-repo. helmrelease carries the same complexity — concurrency, timeouts, live progress, two output modes — and stays thin

⚠ Where they stop

  • "Thin wrapper" can be over-applied. Pushing --output auto, progress display, or exit-code mapping into services couples them to terminal semantics. Thin means no decisions that survive the surface, not no code
  • There is no mandatory use-case layer. helmrelease and events reach portability with services alone; an app/ layer over charts list is ceremony. manifest_validation/app.py exists because that context needs it
  • Frozen results beat printing. DevelopmentClusterService, EphemeralTestClusterService and LocalBootstrapExecutor return frozen outcomes and narrate through an injected progress callback
  • Enforcement is mechanical. The TID251 rule guards the adapter boundary; layering tests keep Rich, Typer and sys.exit out of services
The shape in one sentence: 25 public commands plus the hidden Renovate finalizer enter typed service boundaries — one *Request in, one frozen *Result out — with wire projections in services/*/wire.py, construction in composition.py, and rendering, device policy and process exit confined to cli/. validate clean is the one deliberate exception: a small guarded artifact-removal command.

The DFS — install_plan mechanics (code-side deep dive: Shared domain → dependency graphs)

Algorithm (post-order DFS, keyed by (chart, profile))

  • permanent set = fully emitted nodes: re-visits short-circuit, so shared deps appear once
  • temporary stack = the current descent path: hitting a key already on it is a cycle ⇒ DependencyCycleError: dependency cycle detected: a:minimal -> b:minimal -> a:minimal — the message is the full chart:profile chain

  • the same chart/profile identity is emitted once; the requested target naturally appears after its prerequisites

Model rules

  • apiVersion and kind are Literals; no other envelope is accepted
  • ResourceMetadata.name, release name, namespace and profile are all lowercase DNS labels of at most 63 characters
  • LocalStackSpec.releases declares min_length=1 — an empty stack is not a stack

  • _relative_path inspects the authored spelling before Path normalizes it away: empty strings, backslashes, leading /, and any ""/"."/".." segment are rejected

  • Existence is checked too: spec.cluster.config must be a file, every release.chart a directory with a Chart.yaml, and every release.values entry a file

The status model — services/helmrelease/state.py, the vocabulary shared by monitor, test, promote, wire and the renderer

state.py is the single vocabulary for the whole vertical: one Verdict enum shared by monitor and test, a closed Reason set, a Stage discriminator, and the phase tables that connect all three to events.lifecycle.PromotionPhase. Every consumer — renderer, wire projection, CLI exit code, event emitter — reads the same definitions instead of re-deriving run state. "Which verdicts count as success" has exactly one definition, PASSING_VERDICTS, and the promotion timeline has both a start and an end because the same module owns both brackets.

The four types

  • Verdict — one enum for both services: ready · passed · failed · timed-out · skipped-suspended · skipped-not-ready · no-match. PASSING_VERDICTS is the single definition of success — the service, the CLI's headline count and the process exit code all read that one set
  • Reason — the closed set we author. Typed Reason | str on purpose: the terminal-Ready path passes through whatever Flux wrote into the CRD condition, so that tail is open and typed honestly rather than pretending otherwise (coerce_reason)
  • Stage — rollout or helm-test. Needed because Verdict.FAILED means abandoned from monitor and helm_test_failed from test; the phase table keys on the (Stage, Verdict) pair rather than the verdict alone
  • PromoteStatus — the six terminal states of a promote run (detailed on the PromoteService panel)

Three phase tables — data, not if-chains

START_PHASE Stage → the opening bracket rollout → WAITING_ROLLOUT helm-test → HELM_TEST_RUN TERMINAL_PHASES (Stage, Verdict) → phases, in order (rollout, ready) → ROLLOUT_OK (rollout, failed) → ABANDONED (rollout, timed-out) → ABANDONED (helm-test, passed) → HELM_TEST_OK, PROMOTED (helm-test, failed) → HELM_TEST_FAILED PROMOTE_PHASE PromoteStatus → phase | None
  • Pairs absent from the table emit nothing, on purpose. A run where every HelmRelease was suspended, or where none matched, is not a state transition — recording one would put a phantom endpoint on the timeline
  • A green helm test is what makes a promotion verified, so it alone carries PROMOTED. A pipeline that runs monitor alone closes at ROLLOUT_OK and never claims promoted — rollout is not proof
  • StrEnum is deliberate: members compare and hash as their wire strings and json.dump writes them verbatim, so the typed vocabulary and the --output json contract pinned by the golden files are the same bytes

Lifecycle emission — telemetry.PromotionTelemetry

9 of the 11 PromotionPhase members are emitted. The single subprocess chokepoint. Every external binary the tool touches — helm, kubectl, kind, git, gh, HelmRelease CRD reads, kubeconform, kyverno, mise — runs through run(). The whole API

run(args, *, cwd=None, check=True, capture=True, timeout=None, env: Mapping[str, str] | None = None) → CommandResult CommandResult(frozen): args: tuple · returncode stdout · stderr ("" when capture=False) redact(args) → display string, credential values masked

A Protocol with one method — so integrations can share one instance (Helm's per-runner version memo keys on it) and any object of the right shape is a valid fake.

Contract semantics

  • check=True (default): rc≠0 ⇒ ExternalCommandError — detail is stderr.strip() or stdout.strip(), and the structured .stderr/.returncode fields are populated at every raise site, so a caller never has to parse the message string
  • check=False: caller reads result.returncode itself — how CI/ephemeral testing turn a helm test rc≠0 into a richer error, and how hr/test avoids aborting a fan-out
  • capture=False: child inherits the terminal; stdout/stderr come back as ""
  • timeout: seconds or None ⇒ CommandTimeout. The hr monitor/test budgets land here after parse_duration
  • env: overlaid on os.environ, never substituted for it — a bare env= drops PATH, and the next thing that happens is the tool isn't found, which surfaces as MissingToolError and reads like a broken install rather than like the caller having scoped one variable. Lets a caller pin KUBECONFIG or DOCKER_HOST to a single invocation
  • credential redaction: --set, --set-string, --token, --password, --docker-password values are masked in every error message. --set key=value keeps the key so the message still says which setting failed — rendered errors travel into logs and event payloads

① install_plan — the DFS, precisely

The two bookkeeping structures

  • temporary is a list, not a set — it is the current descent path in order, so the cycle error can render the actual chain: DependencyCycleError: dependency cycle detected: a:minimal -> b:minimal -> a:minimal (path + the repeated key appended)
  • permanent is a set — fully-emitted nodes; re-visits short-circuit, so a dep shared by two branches is emitted once
  • nodes are keyed by (chart, profile) pairs — the same chart under two profiles is two distinct plan entries
  • post-order emit: a node is appended after its requires ⇒ dependencies always precede dependents

Deduplication and target ordering

  • visiting a permanently emitted chart/profile is a no-op, so identical shared requirements appear once
  • plain post-order DFS naturally emits the requested root after all of its prerequisites
  • net invariant: every chart/profile identity appears once and dependencies precede dependents
  • the same chart under different profiles remains distinct and may therefore execute more than once

Two fields with subtle ownership

  • error_type is set by the phase function alongside status — it's what separates a validation FAIL (exit 1) from a tool crash ("tool" → exit 2) from a spec parse error ("spec" → exit 3). Status says what, error_type says why it's not the chart's fault
  • elapsed_seconds is populated by the runner, not the phase fn (wall-clock around the call) — surfaced only with --timings
  • skip_cause is structured orchestration data, not presentation text: a consumer distinguishes an authored-disabled validator from one blocked by an upstream failure without parsing detail
  • validator_results preserves concrete provider identity while phases remains the compatible category aggregate consumed by existing JSON/Markdown and exit-code logic
  • spec_errors on RunResult holds spec-level failures that prevented rows from existing at all (corrupt chart-lifecycle.yaml, unsupported root version) — a run can exit 3 with zero rows
  • all four are frozen=True — results are values; the runner's worker threads can share them without locks
Composition, not inheritance: validation owns ManifestValidationSpec, selection, cases and outcomes; the shared chart domain owns HelmChart. ManifestValidationTarget composes them. Output-path helpers reject unsafe segments, enforce containment beneath the run root and guard cleanup against symlink/traversal escape.

Extraction order (dependency-safe)

shared domain + plumbing

Move the current boundaries intact; the split is complete and layering-tested. This gives every later package the same metadata, graph and error contracts.

operator safety + CI gates first

Wire an explicit CLI cluster context into Settings and every Container. Then gate mypy, actionlint and formatting, remove stale CI backlog comments, and align the supported Python version. These prevent wrong-cluster actions and keep the clean baseline clean.

integrations + their tests

Carry the Helm dependency-policy edge deliberately. The current repository gate is 1,031 passing tests, 6 explicitly deselected. Lifecycle coverage includes compiler determinism, impact reasons, bootstrap identity, plan projection, executor ordering, local-resource strictness and path containment, and CI matrix projection. Carry integrations/renovate.py here too — it is a leaf adapter, and its config-validation tests keep the repository's Renovate JSON honest. The deselected integration set exercises real external-tool boundaries separately from the fast default gate.

manifest validation intact

Move the flat manifest_validation/ bounded context together: catalog, planner, compiler, models, spec, app, runner, phases, progress and wire. Callers already import the owning modules directly.

delivery + optional events

Promotion, monitoring, Helm testing, and publishing expose typed results and versioned wire projections where needed. If event querying becomes a product capability, add a typed query service rather than expanding scripts. Keep persistent development and ephemeral test policies explicit.

surfaces + adoption guide

Adapt the existing thin handlers and renderers to the host, then publish one concise operator/developer guide matching the CI commands and cluster-selection contract. Add an API only when there is a caller.

Bottom line: the domain/plumbing split, manifest-validation package, headless services, composition root, typed results, ordered lifecycle execution, the authored local-environment resources behind a provider seam, Renovate-backed intake, OCI publication, and delivery telemetry are implemented. Keep persistent development and ephemeral testing explicit; do not add a base spec, repository protocol, dependency-only command, shared workflow engine, or API without a real second use. Remaining product work includes a dedicated PR-merge wait, an optional event-query capability, cleanup of genuinely empty packages, and concise operator guidance.
