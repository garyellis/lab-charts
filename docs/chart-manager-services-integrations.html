chart-manager upgrade

cli/upgrade.py · 251 ln · 2 commands (1 hidden) · registered on the root appdependency intake

The intake stage that Flow 0 used to mark planned. Ask Renovate to discover dependency updates for one wrapper chart and turn the completed update into one repeatable pull request. The module's own docstring states the split precisely: "the service owns discovery, preflight, isolated worktree mutation, and PR idempotency. This module owns only Typer's flag shape and stable rendering."

upgrade --path CHART_PATH --dry-run --format text|json → UpgradeService.upgrade(UpgradeRequest) → UpgradeResult upgrade-finalize --path CHART_PATH --data-file PATH (envvar RENOVATE_POST_UPGRADE_COMMAND_DATA_FILE) --format … → UpgradeFinalizer.finalize(FinalizeRequest) → FinalizeResult # hidden=True

Why two commands, and why one is hidden

  • upgrade is what an operator or a workflow runs. It resolves Path(".") as the repository root and never switches branches, stages files or commits in the caller's checkout — Renovate does its own platform checkout
  • upgrade-finalize runs inside Renovate's update branch, called back by postUpgradeTasks.commands. hidden=True keeps it out of --help: it is machine surface, not operator surface
  • The callback data file is taken from --data-file or the RENOVATE_POST_UPGRADE_COMMAND_DATA_FILE envvar, and a missing value is an explicit ChartManagerError rather than a silent no-op
  • Both commands go through _container() module-level factories — the same monkeypatch seam every other group uses

One renderer, two result types

  • _wire_payload projects either UpgradeResult or FinalizeResult onto one schema_version: 1 contract, preferring a result's own to_dict() and falling back to asdict
  • _render_text emits every contract field in a fixed order, including absent ones (-) — so a script grepping the text output does not break when a field is null
  • _json_value normalizes Path, Enum, mappings and tuples, and JSON is dumped sort_keys=True — deterministic bytes for automation
  • This is the one place the surface carries real logic. It is renderer-shaped (projection + formatting) rather than orchestration, but the _first(..., "current_wrapper_version", "current_version", …) alias-chasing is a smell: if the two result dataclasses converged on one field vocabulary, _wire_payload would shrink to a pass-through, and a second surface would not have to re-derive the same aliases
The hidden command is the security boundary, and it is treated like one. Renovate's post-upgrade execution is privileged by nature, so the trust is pinned in configuration rather than in the CLI: renovate-global.json sets allowShellExecutorForPostUpgradeCommands: false and constrains allowedCommands to a single anchored regex — ^chart-manager upgrade-finalize --path (?:[A-Za-z0-9][A-Za-z0-9._-]*/)+[A-Za-z0-9][A-Za-z0-9._-]*$. Nothing else in the repository can be executed from a Renovate branch, and the path shape is validated again by resolve_chart_path before any file is read. See the upgrader service panel for the containment rules.
Outcome vocabulary (UpgradeResult.outcome, rendered verbatim): dry_run · no_changes · pr_open (this run opened it) · pr_updated (a PR on the chart's deterministic branch already existed) · status_unknown. That last one is the interesting one — it is emitted when gh could not answer, so the command reports "Renovate ran, PR state unverified" instead of guessing no_changes. The failed lookup is also appended to diagnostics. Operator-facing detail lives in docs/renovate-upgrades.md.

Why it works

  • One frozen request object per command. Every flag lands on MonitorRequest/TestRequest/PromoteRequest; the service validates its own fields. Nothing is "resolved" in the callback
  • Results carry the verdict. result.ok drives typer.Exit(1) — the CLI never decides pass/fail
  • Rendering is a separate module. The Rich renderers live in helmrelease_render.py; the services are rendering-agnostic and import no Rich. (True — but this panel originally stopped here, and that was the mistake. See below.)
  • DI through overrideable factories, backed by the container. _make_monitor_service / _make_test_service / _make_promote_service are still module-level so tests swap them, but their bodies now delegate to _container(). The seam survived the composition root instead of being replaced by it
  • Interaction is a port, not a dependency. _confirm_downgrade is passed in as a callable, so PromoteService can ask a question without knowing what a terminal is. A Slack surface passes a callback that posts a button; a REST surface passes lambda *_: False and gets PromoteStatus.ABORTED back to map to 409

The only wrinkles

  • _resolve_output_mode raises ChartManagerError for a bad --output where typer.BadParameter would be the local idiom — trivial
  • The progress callback is wired only in pretty mode; JSON mode passes None. Correct, but it means progress events have no non-terminal consumer yet — a websocket surface would want them
  • The claim "portable as-is" was wrong — and the counter-example is the most instructive thing on this page. cli/helmrelease_render.py held _SCHEMA_VERSION = 1 and six _serialize_* helpers: a versioned wire contract living in cli/, private-by-underscore. A REST endpoint returning monitor results would have had to import upward from the CLI into a new surface, or re-serialize and immediately ship two divergent schemas both claiming schema_version: 1. The shape was wrong too — render_monitor_json(result, file) took an IO[str] and wrote+flushed; an API wants a dict
  • Resolved: services/helmrelease/wire.py now owns SCHEMA_VERSION (public, no longer underscore-private), monitor_to_dict and test_to_dict — pure result → dict, no file, no format=. The CLI's JSON path is now three lines of json.dump. Byte-identical output was proven by writing golden snapshots against the pre-refactor code, then re-running them untouched
  • Why it was easy to miss: a JSON serializer looks exactly like presentation until you ask whether a second surface wants the identical bytes. That is test ② on the verdict panel, and this group is why it exists. Note the asymmetry that gave it away: validate's JSON_SCHEMA_VERSION was public and in services/, helmrelease's was private and in cli/ — two versioned contracts, two homes, two visibilities. That inconsistency was the tell that "wire contract" had no name in the codebase
  • With that closed, the group genuinely is portable: a FastAPI route is ~10 lines around the same three calls, and it returns the same dict the CLI prints

Two tests, and you need both

① Does it change the answer, or only the appearance? --output auto changes only how a result is displayed — CLI. lab-<env> changes which namespace manifests render into, so it changes what passes validation — service. _detect_apps_domain determines the URL a user is told to open — service. ② Would a second surface want this identically, or necessarily differently? This one sorts within the surface bucket, and it is the test the original three-bucket cut was missing. Identically ⇒ it is a contract, push it below cli/: an API, a Slack app, and a web UI all want the exact same JSON — if they don't get it from one function they diverge silently, both claiming schema_version: 1. Necessarily differently ⇒ it stays up: an HTTP server has no terminal, so there is nothing to share about isatty or a Rich Live table. Together the two tests produce the split on the surface panel — 11/5/12 as assessed, 2/0/26 as it stands now.
The boundary that keeps ② from overshooting: push projections down, not rendering. to_json(result) -> dict in a service is right; emit(result, fmt="json", color=False, console=…) is wrong — the moment a service grows a format= parameter it starts growing color= and width=, and you have moved the UI down instead of the contract. Services expose pure result → dict/str functions; the surface picks one and does all the I/O.

The second finding: the leak went both ways closed

Orchestration leaked up into cli/; presentation leaked down into services/. Three services imported Rich and held a Console — lab.py, sandbox.py, cluster_bootstrap.py — and DevelopmentClusterService.up/sync/down/delete plus EphemeralTestClusterService.run all returned None, so their continue-on-error accounting existed only inside a printed table. Where the reasoning is strongest — and where I'd push back

✓ The argument holds

  • Multi-surface is the real forcing function. REST / GraphQL / RPC / Slack are not hypothetical extras — each one re-answers "what does this command mean", and at assessment time 11 commands had that answer only inside a Typer callback
  • The evidence is concrete, not aesthetic. validate run constructs RunResult itself; deps checks synthesizes a domain object no service knows about. These are not "the file is long" complaints
  • Testability follows for free. Assembly in a command body is reachable only through CliRunner; the same logic in a use-case object is a plain unit test with no terminal
  • The proof already exists in-repo. helmrelease hit the same complexity — concurrency, timeouts, live progress, two output modes — and stayed thin. The pattern is proven here, not imported from a book

⚠ Where I'd temper it

  • "CLI should be a thin wrapper" can be over-applied. Pushing --output auto, progress display, or exit-code mapping into services would couple them to terminal semantics — the exact mistake lab/sandbox already made. Thin means no decisions that survive the surface, not no code
  • Don't add a use-case layer everywhere. helmrelease and events reached portability with services alone. A mandatory app/ layer over charts list is ceremony. Add it where validate needs it and let it spread only on evidence
  • Type B was the cheaper, higher-value fix — confirmed. Returning _RunSummary from DevelopmentClusterService.up unblocked five commands and touched one file. It shipped first, before the validate extraction, and that ordering held up
  • Sequence matters. Building a second surface before extracting is how duplication becomes permanent — the copy gets written once and then diverges silently, exactly as deps checks would have. Still the live risk for anyone adding an api/ package; the TID251 rule now guards it on day one

The DFS — install_plan mechanics (code-side deep dive: Shared domain → dependency graphs)

Algorithm (post-order DFS, keyed by (chart, profile))

  • permanent set = fully emitted nodes: re-visits short-circuit, so shared deps appear once
  • temporary stack = the current descent path: hitting a key already on it is a cycle ⇒ DependencyCycleError: dependency cycle detected: a:minimal -> b:minimal -> a:minimal — the message is the full chart:profile chain
  • each node appended after its requires ⇒ dependencies always install first
  • _dedupe_keep_last_target: if the target chart also appears as someone's dependency, the earlier entry is dropped and the final target=True entry kept — the target is installed exactly once, and last
  • same chart under two different profiles = two distinct plan entries (key is the pair, not the chart)

The finalizer — the part that does not trust its own branch

Deterministic version rule

read Chart.yaml at the baseline ref via git show HEAD:<chart>/Chart.yaml, and the current one from disk
updates come from the Renovate data file; if it is absent, _chart_dependency_diff infers them by diffing the two dependency lists
keep only qualifies updates — a Helm chart dependency or a container image. Everything else cannot move a wrapper version
any qualifying major ⇒ baseline.major + 1 . 0 . 0; otherwise baseline.patch + 1. No minor bumps by design
write only what changed: Chart.yaml if the version is not already at target, changelog.md if the heading is not already present

Why it is replay-safe

  • The target is computed from the baseline, never from the current file. Renovate or the job runner can retry the callback any number of times and the answer is identical
  • The current version is allowed to be exactly baseline or target. Anything else raises — a hand-edited or double-bumped branch is a hard error, not a third bump
  • A version that diverged from baseline with no qualifying update also raises: the wrapper cannot drift on a non-dependency change
  • Changelog idempotency is a heading-presence check (## <target>), so a re-run prepends nothing
  • Qualifying updates missing dependency/currentValue/newValue raise rather than producing a changelog line like dependency: ->
  • ruamel round-trip with preserve_quotes keeps the Chart.yaml diff to the version line — same discipline as the promote editor

The status model — services/helmrelease/state.py, the vocabulary shared by monitor, test, promote, wire and the renderer

Before this module the vertical carried three disconnected vocabularies: two Literal verdict sets (monitor.Verdict and test.TestVerdict, overlapping by four members with no shared supertype), a free-form reason: str whose value set was implicit across ~24 literal call sites, and events.lifecycle.PromotionPhase, which nothing in monitor or test could reach. Every consumer — renderer, wire projection, CLI exit code — re-derived run state independently. That is how "which verdicts count as success" ended up copy-pasted into six places across two layers, and how the promotion timeline ended up with a start and no end.

The four types

  • Verdict — one enum for both services: ready · passed · failed · timed-out · skipped-suspended · skipped-not-ready · no-match. PASSING_VERDICTS is the single definition of success — the CLI's headline count and the process exit code now read the same set
  • Reason — the closed set we author. Typed Reason | str on purpose: the terminal-Ready path passes through whatever Flux wrote into the CRD condition, so that tail is open and typed honestly rather than pretending otherwise (coerce_reason)
  • Stage — rollout or helm-test. Needed because Verdict.FAILED means abandoned from monitor and helm_test_failed from test; the phase table keys on the (Stage, Verdict) pair rather than the verdict alone
  • PromoteStatus — the six terminal states of a promote run (detailed on the PromoteService panel)

Three phase tables — data, not if-chains

START_PHASE Stage → the opening bracket rollout → WAITING_ROLLOUT helm-test → HELM_TEST_RUN TERMINAL_PHASES (Stage, Verdict) → phases, in order (rollout, ready) → ROLLOUT_OK (rollout, failed) → ABANDONED (rollout, timed-out) → ABANDONED (helm-test, passed) → HELM_TEST_OK, PROMOTED (helm-test, failed) → HELM_TEST_FAILED PROMOTE_PHASE PromoteStatus → phase | None
  • Pairs absent from the table emit nothing, on purpose. A run where every HelmRelease was suspended, or where none matched, is not a state transition — recording one would put a phantom endpoint on the timeline
  • A green helm test is what makes a promotion verified, so it alone carries PROMOTED. A pipeline that runs monitor alone closes at ROLLOUT_OK and never claims promoted — rollout is not proof
  • StrEnum is deliberate: members compare and hash as their wire strings and json.dump writes them verbatim, so adopting these types changed no byte of the --output json contract pinned by the golden files

9 of the 11 PromotionPhase members are now emitted; before this, 3 were. CommandRunner (Protocol) + SubprocessRunner + CommandResult

plumbing/commands.py · 175 lnsubprocess kernel

The single subprocess chokepoint. Every external binary the tool touches — helm, kubectl, kind, git, gh, HelmRelease CRD reads, kubeconform, kyverno, mise — runs through run(). One place owns argv execution, output capture, environment overlay, timeout coercion, credential redaction and failure wrapping. Exactly one bypass exists in the whole tree: Kubectl's port-forward uses subprocess.Popen directly, because a long-lived detached daemon can't ride a synchronous run().

CommandRunner is now a Protocol; SubprocessRunner is the implementation. This is the doc's best example of a seam that could not evolve. The name used to be the concrete class, and 19 bespoke subclasses across 17 test files inherited from it — each hand-copying the run signature, none calling super().__init__. Adding a single keyword therefore broke every fake at once. That is the documented reason env was missing for years, and in turn why Kubectl and Kind had nowhere to put a cluster address and read the ambient one instead. A missing parameter on a base class silently became an architectural constraint two layers up. Structural typing means a fake satisfies the seam by shape; the 19 subclasses collapsed into one FakeCommandRunner in tests/conftest.py, and adding env was then a one-line edit.

A Protocol with one method — so integrations can share one instance (Helm's per-runner version memo keys on it) and any object of the right shape is a valid fake.

Contract semantics

  • check=True (default): rc≠0 ⇒ ExternalCommandError — detail is stderr.strip() or stdout.strip(), and .stderr/.returncode are populated (they used to be left empty by the kernel — the test fakes were more capable than production)
  • check=False: caller reads result.returncode itself — how Ci/Sandbox turn a helm test rc≠0 into their own richer error, and how hr/test avoids aborting a fan-out
  • capture=False: child inherits the terminal; stdout/stderr come back as ""
  • timeout: seconds or None ⇒ CommandTimeout. The hr monitor/test budgets land here after parse_duration
  • env: overlaid on os.environ, never substituted for it — a bare env= drops PATH, and the next thing that happens is the tool isn't found, which surfaces as MissingToolError and reads like a broken install rather than like the caller having scoped one variable. Lets a caller pin KUBECONFIG or DOCKER_HOST to a single invocation
  • credential redaction: --set, --set-string, --token, --password, --docker-password values are masked in every error message. --set key=value keeps the key so the message still says which setting failed — rendered errors travel into logs and event payloads

The two escape hatches the kernel closes — TimeoutExpired and FileNotFoundError

kills the child and raises subprocess.TimeoutExpired — which callers up-stack know nothing about

partial output is salvaged from the exception: _decode(exc.stderr) or _decode(exc.stdout) — stderr first, same preference as the failure path
_decode
the partial output on TimeoutExpired is bytes-or-str depending on text mode; coerced defensively — None → "", bytes → utf-8 (errors=replace), anything else → str()

parse_duration

plumbing/duration.py · 26 lnone function

Kube-style duration strings → float seconds. Deliberately narrow: exactly the units kubectl --timeout accepts, nothing more.

Accepted formats

"60s" → 60.0 "5m" → 300.0 "1h" → 3600.0 "90" → 90.0 bare number = seconds (int or float) "1.5h" → 5400.0 float multipliers work "" · "5d" · "abc" → ChartManagerError: invalid duration: …

Units table: s · m · h only. No days, no compound (1h30m) — "5d" fails on float("5d") since d isn't a unit.

Who calls it

  • Kubectl — converts the wait-gate timeout string into a monotonic deadline for its poll loops
  • hr MonitorService — __post_init__ budget guards (per-poll < per-HR ≤ total) plus deadline math in the poll loop
  • hr TestService — same budget-triangle validation + subprocess-slack conversion for the CommandRunner timeout

Why ChartManagerError and not ValueError: a bad --timeout 5x flag is operator input, so it must ride the exit-1 funnel as a one-liner instead of a traceback.

Note the asymmetry: helm-facing timeouts (cluster-test configuration's timeout: 10m) are passed to helm verbatim as strings — helm parses its own durations. Only chart-manager's own deadline arithmetic (kubectl polls, hr budgets) needs seconds, and that's the only place this function appears.

① install_plan — the DFS, precisely

The two bookkeeping structures

  • temporary is a list, not a set — it is the current descent path in order, so the cycle error can render the actual chain: DependencyCycleError: dependency cycle detected: a:minimal -> b:minimal -> a:minimal (path + the repeated key appended)
  • permanent is a set — fully-emitted nodes; re-visits short-circuit, so a dep shared by two branches is emitted once
  • nodes are keyed by (chart, profile) pairs — the same chart under two profiles is two distinct plan entries
  • post-order emit: a node is appended after its requires ⇒ dependencies always precede dependents

The target re-append + dedupe pair

  • re-append branch: visiting an already-permanent node normally no-ops, except when it's the target — then a fresh target=True entry is appended anyway
  • _dedupe_keep_last_target then removes any earlier entry for the same (chart, profile), keeping the last — i.e. the target=True one
  • net invariant: the target appears exactly once, last, flagged — even if it also occurs as someone's dependency
  • honest note: with today's single-root call (visit(target) first, and a dep looping back to the target would be a cycle), plain post-order already yields target-last — the pair makes the invariant explicit rather than incidental, and keeps it if multi-root plans ever appear

Worked example — dedupe mechanics in isolation

input [a, t, b, t*] t seen twice; * = target=True walk a → keep t → keep (for now) b → keep t* → t already seen: strip earlier t, append t* at the end output [a, b, t*] target once, last, flagged

request built by the composition root's factory → env-only invocation (RENOVATE_CONFIG_FILE · optional RENOVATE_ADDITIONAL_CONFIG_FILE · RENOVATE_CONFIG · RENOVATE_DRY_RUN · RENOVATE_TOKEN) → renovate <owner/repo>. Renovate does its own platform checkout; the caller's working tree is never touched
— Renovate's branch —
deps and image tags updated, then postUpgradeTasks runs chart-manager upgrade-finalize --path <chart> with a handlebars-rendered data file. Only that one command shape is permitted
UpgradeFinalizer
git show HEAD:<chart>/Chart.yaml for the baseline → keep qualifying (Helm-dependency or container-image) updates → major if any update is major, else patch, computed from the baseline → write Chart.yaml and prepend changelog.md, each only if not already at target. A retry recomputes the identical answer
second gh probe
before/after comparison decides the outcome: pr_open (appeared this run) vs pr_updated (already existed) vs no_changes; a failed probe wins over both as status_unknown
UpgradeTelemetry
for pr_open, or pr_updated with a different proposed version, emit BuildPhase.PR_OPEN using correlation_id=<chart>@<proposed_version> and build_correlation_id=<repository>#<pr_number>. Unchanged re-runs and non-proposal outcomes emit nothing; sink failures are non-fatal
renderer
fixed-order text with - for absent fields, or sort_keys JSON at schema_version 1. Renovate stderr lines and any PR-lookup failure ride along in diagnostics

Flow 5 · event write path — the audit trail

CLI / automatic emitters
events build|promote, UpgradeTelemetry, PromoteService and PromotionTelemetry call EventWriter.build()/promote(), which assembles PlatformLifecycleEvent — chart/version join id, phase enum, PR ids, git sha, optional backfill timestamp
get_event_store()
EVENTS_BACKEND → Cosmos (default), DynamoDB, or none; the store is resolved lazily on first write and memoized with the writer
adapter
Cosmos: partition /chart_name, id=uuid · DynamoDB: HASH chart_name, RANGE event_id=timestamp#uuid · none: NullEventStore discards silently. correlation_id=chart@version remains the timeline join key within a chart partition
SDK client factory
env-driven auth incl. local emulators (dynamodb-local endpoint, cosmos emulator TLS overrides; tested via dynamodb.kind.local VirtualService)
shared failure policy
events.failure.emit_non_fatal serves the CLI, upgrader and helmrelease telemetry. Store errors log a warning and are swallowed unless strict mode is requested; the CLI prints emitted … only after a successful write

Extraction order (dependency-safe)

shared domain + plumbing

Move the current boundaries intact; the split is complete and layering-tested. This gives every later package the same metadata, graph and error contracts.

operator safety + CI gates first

Wire an explicit CLI cluster context into Settings and every Container. Then gate mypy, actionlint and formatting, remove stale CI backlog comments, and align the supported Python version. These prevent wrong-cluster actions and keep the clean baseline clean.

integrations + their tests

Carry the Helm dependency-policy edge deliberately. The current repository gate is 973 passing tests, 6 explicitly deselected. Lifecycle coverage includes compiler determinism, impact reasons, evidence safety, status freshness, live ownership, executor ordering and CI matrix projection. Carry integrations/renovate.py here too — it is a leaf adapter, and its config-validation tests keep the shipped JSON honest. The one deselected test worth wiring into the host's CI is test_renovate_extraction.py: it runs the real Renovate binary to prove chart dependencies and literal image: tags are actually extracted, which is the failure mode that otherwise surfaces as a silently missed upgrade.

manifest validation intact

Move the flat manifest_validation/ bounded context together: catalog, planner, compiler, models, spec, app, runner, phases, progress and wire. Callers already import the owning modules directly.

delivery + optional events

Add promote JSON. If audit events remain, make them explicitly enabled, backend-lazy and pre-provisioned; add a typed query instead of scripts. Keep Lab and Sandbox separate—their execution semantics intentionally differ.

surfaces + adoption guide

Adapt the existing thin handlers and renderers to the host, then publish one concise operator/developer guide matching the CI commands and cluster-selection contract. Add an API only when there is a caller.

Bottom line: the domain/plumbing split, manifest-validation package, headless services, composition root, typed results and reliability work are complete, and Renovate-backed intake now opens its own build lifecycle timeline. Keep Lab and Sandbox explicit; do not add a base spec, repository protocol, shared workflow engine or API without a real second use. Remaining production work is small and ordered: explicit CLI cluster targeting; CI gates and Python alignment; service-owned validate clean; promote JSON; backend-lazy, pre-provisioned events with a typed query path if audit is retained; migration of existing event stores to chart_name partitioning; deletion of empty image_resolver/; and one concise adoption guide. Publish and PR-merge wait remain separate product capabilities, not port blockers — with intake built, they are the last two amber nodes in Flow 0.
